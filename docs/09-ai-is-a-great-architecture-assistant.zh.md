# 架构需要碰撞，AI 是最好的陪练

一个人做架构，不管经验多深，都有盲区。你熟悉的方案会变成思维定式，你习惯的模式会挡住其他可能性。架构能力的提升从来不是靠一个人闷头想出来的，而是靠碰撞——看到不同的实现方式，才能反过来审视自己的假设。

而且架构层面的每一个改进，影响力都是指数级的——它不是改一个函数、修一个 bug，而是决定了后续所有功能的实现方式和复杂度。一个好的架构决策，能让接下来几十个功能的实现变简单；一个差的架构决策，会让每一步都在还债。所以架构上的碰撞，回报远比代码层面的碰撞大。

以前这种碰撞只能来自同事 review、技术讨论、或者读别人的代码。现在 AI 能在几分钟内给出一个完整的、可运行的实现。它的方案不一定是最优的，但它提供了一个不同的视角，让你有具体的东西可以审视和碰撞。这也是 AI 最被低估的价值——不只是帮你写代码，而是帮你在架构层面产生碰撞，而这个层面的每一点改进，都会成倍放大到整个项目。

我做过 nginx njs 模块的开发，那是一个生产级的 JS 运行时嵌入方案，架构经过多年打磨。jsmock 的架构方向我心里有数。但这次 AI 引入的一些概念——deferred、dispatch——让我对已有的想法产生了新的改进思路。不是 AI 的架构能力比我强，而是它的实现角度跟我不同，这个不同本身就有价值。

## 问题

我希望 jsmock 支持 top-level await。用户应该能在模块顶层写异步代码：

```js
const sleep = (ms) => new Promise(r => setTimeout(r, ms));
await sleep(100);

mock.get("/hello", (req) => {
    return new Response("hello-after-sleep");
});

export default { listen: 18094 };
```

这是一个产品需求。我没有给方案，直接扔给了 AI。

## AI 的方案

AI 分析了根因：`await sleep()` 挂起模块求值，`JS_EvalFunction` 返回了，但 `mock.get()` 还没执行，路由表是空的。紧接着代码匹配路由，404。

然后给了一个方案，核心改动三处：

1. 提取 `js_qjs_dispatch_request` 函数——把路由匹配、handler 调用、Promise 处理从 `js_qjs_handle_request` 里拆出来
2. 模块求值后检查 pending timer，有就 deep-copy 请求到堆上，走 **deferred** 路径
3. timer 回调里检查完成条件，模块求值结束后再 **dispatch**

方案能跑通，74 个测试全过。

## deferred 和 dispatch

让我产生新想法的不是方案本身，而是 AI 引入的两个概念：**deferred** 和 **dispatch**。

原来的 `js_qjs_handle_request` 是一个 200 多行的大函数。模块求值、路由匹配、handler 调用、Promise 状态判断全揉在一起。AI 为了解决 top-level await，把请求处理拆成了两个阶段：

- **模块求值**——加载字节码、执行模块、注册路由
- **请求分发（dispatch）**——匹配路由、调用 handler、处理响应

当模块求值没完成时，请求进入 **deferred** 状态——存起来，等模块求值结束后再 dispatch。

```c
/* 模块求值后，检测是否需要 defer */
if (exec.timeouts != NULL) {
    /* deep-copy 请求到堆上，走 deferred 路径 */
    ...
    exec.req = hreq;
    goto deferred;
}

/* 模块求值完成，直接 dispatch */
int drc = js_qjs_dispatch_request(&exec, req);
```

timer 回调里，模块求值完成后触发 dispatch：

```c
/* deferred 的请求，等 timer 跑完后 dispatch */
if (exec->conn && exec->req != NULL && exec->timeouts == NULL) {
    js_http_request_t *dreq = exec->req;
    exec->req = NULL;
    int drc = js_qjs_dispatch_request(exec, dreq);
    ...
}
```

看到这个拆分的时候，我脑子里的想法不是"这个 top-level await 的问题解决了"，而是：**模块求值和请求分发本来就不该在一个函数里。**

AI 为了解决 top-level await，被迫把这两个阶段拆开了。但拆开之后我看到的是：模块求值是初始化，请求分发是运行时，它们天然独立。`js_qjs_dispatch_request` 这个函数的签名——接收一个 `exec` 和一个 `req`，不关心模块是怎么加载的——这个结构本身就有价值，它让我对后续的架构演进有了更具体的想法。

AI 不会想到这一层。它在当前架构里做到了最好——方案干净，细节正确，生命周期处理没出错。但它不会主动说"我们是不是该换个架构了"。它解决的是眼前的问题，不会质疑框架本身。

而我从它的实现里看到了下一步怎么走得更清楚了。

## 概念比代码值钱

回头看这次协作，AI 写了两三百行代码，改了 3 个文件，新建了 2 个测试文件。这些代码能用，测试全过。但对我价值最大的不是这些代码，而是 **deferred** 和 **dispatch** 这两个概念。

它们让"模块求值"和"请求分发"这两个阶段变得可见了。之前揉在一个大函数里，你看不清边界。AI 为了解决一个具体问题，把它们拆开了。拆开之后，边界清晰了，下一步该怎么走也清晰了。

这种体验以前需要跟人讨论才能得到——一个人写代码，另一个人 review，在具体的实现上碰撞，冒出更好的抽象。现在 AI 能在几分钟内给出一个完整的实现，你审视的是真实的、可运行的代码，不是白板上的方框图。概念从代码里长出来，比从讨论里蹦出来更扎实。

AI 可能是目前最好的架构辅助工具。不是因为它的架构能力强——它不会质疑现有框架，不会主动提出更好的方向。而是因为它能快速产出具体实现，让你有东西可以审视。你本来就有方向感，但方向感是模糊的。看到 AI 的实现，模糊的直觉变成了清晰的判断。这种从具体代码中提炼抽象的过程，是架构思考最有价值的部分。AI 把触发这个过程的成本降到了接近零。

## 深水区

这次 AI 的实现解决了 top-level await，但审视代码后，我发现当前异步架构的改进空间不小。

比如 `req.text()` 目前是同步返回字符串，但按 Web 标准它应该返回 Promise。这不只是 API 合规的问题——顺着这条线往下推，会牵出一连串架构改动：body 不应该在 parse 阶段提前读取，而是等 handler 调用 `req.text()` 时再按需读；body 留在连接的读缓冲区里，请求就必须能引用连接；请求要跨越异步边界存活，就必须从一开始就在堆上分配。每一步都是上一步的逻辑必然。

这些问题指向的是同一件事：当前的异步处理是在同步架构上打补丁，而不是从异步出发设计的。

异步架构设计是几乎所有服务端项目都会遇到的难题，做对了是整个项目的骨架，做错了后面每一步都在还债。jsmock 现在就走到了这个关口——一个 `req.text()` 的返回值类型不对，顺着推下去，请求生命周期、连接模型、内存管理全要重新设计。这是一个非常典型的真实场景。下一篇开始动手，看我怎么带 AI 一步步重构出来。
